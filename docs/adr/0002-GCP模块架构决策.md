# ADR-0002：GCP 云资源管理模块架构决策

- 状态：已接受
- 日期：2026-09-03

## 决策

API Monitor 新增独立的 `gcp` 云厂商模块，模块 ID 为 `gcp`，作为 Google Cloud Platform（GCP）的统一管理入口。模块采用**纯 REST API + OAuth2 service account** 的接入方式，不引入官方 Go SDK 重型依赖，模块结构遵循 Oracle OCI 模块已验证的多文件分层模板。

### 1. REST 优先，不引入官方 SDK

GCP 所有面向本模块的产品（Compute Engine、Resource Manager、Cloud Billing、Cloud Storage、IAM）均提供完善的、稳定的 REST + JSON 接口，并统一使用 OAuth2 Bearer 鉴权。决策使用 Go 标准库 `net/http` 直接调用，理由：

1. 官方 Go SDK（`cloud.google.com/go/*`）依赖链庞大（gRPC、protobuf、genproto），与本项目「SQLite 单进程、低依赖」的架构定位冲突。
2. 模块所需操作均为简单的 REST 请求-响应模式（list/get/insert/delete/操作类 POST），手写轻量客户端的复杂度远低于 SDK 引入的维护成本。
3. 与现有 koyeb 模块的 REST 封装模式（`koyebRequest`：统一拼接 base URL、鉴权头、超时、错误提取）一致，代码风格可复用。GCP 各产品 API 的 base URL 互不相同（compute.googleapis.com、cloudresourcemanager.googleapis.com、storage.googleapis.com、cloudbilling.googleapis.com 等），`client.go` 维护 base URL 映射表，并支持 `GCP_<API>_API_BASE_URL` 环境变量逐端点覆盖，测试指向 mock server。
4. Oracle 模块使用官方 SDK 是基于 OCI「请求签名复杂」的前提；GCP 是 Bearer token 模式，前提不同，决策不同。

### 2. 凭证：Service Account JSON 整体加密落库

GCP 凭证采用 Service Account JSON 密钥文件（含 `client_email`、`private_key` 等）。决策：

1. 完整 JSON 使用现有 `secure.SecureEncrypt` 加密后存入 `gcp_accounts.service_account_json_encrypted` 列。
2. OAuth2 token 交换：用 SA JSON 中的 `client_email` + `private_key` 构造 JWT（header RS256 + claims iss/sub/aud/scope/iat/exp，exp 1h），以 `urn:ietf:params:oauth:grant-type:jwt-bearer` grant type 提交到 token endpoint（取 SA JSON 的 `token_uri`，缺省 `https://oauth2.googleapis.com/token`）换取 access token。注意与 m365 的 client_credentials grant 不同：GCP 私钥在 JWT 断言内，而非 client_secret。
3. 不照抄 aliyun/tencent/koyeb 等模块的明文 token 存储列（历史遗留不一致，见 CONTEXT.md 描述）。GCP 模块从第一版起遵循加密存储基线，与 oracle/m365/cloudflare 一致。
4. Token 缓存在内存（进程级、带过期时间），不做持久化。
5. `private_key` 支持 RSA 全密钥长度；JWT 签名使用 Go 标准库 `crypto` 系列实现，无第三方依赖。

### 3. Scope 策略：只申请所需只读 scope，写操作逐项确认

Service account 的权限边界由 GCP 侧 IAM 角色控制，本模块侧遵循最小权限原则：

- 账号验证、项目列表、资源浏览类：只申请只读 scope。
- 实例启停等写操作：在执行前由前端二次确认，后端执行时申请或复用带写权限的 scope（service account 本身在 GCP 侧需预先授予对应 IAM 角色如 `roles/compute.instanceAdmin.v1`）。
- 模块内不提供 IAM 角色/策略编辑能力（权限配置在 GCP 控制台完成，本模块不代行）。

### 4. 模块结构：照抄 Oracle 模板

```text
backend-go/internal/gcp/
├── service.go              # Service + New + ServeHTTP 路径分发 + open()
├── schema.go               # gcp_accounts 幂等建表
├── account_store.go        # 账号 CRUD + secure 加密 + safeAccount 脱敏
├── types.go                # Account / payload / Normalized* 响应结构
├── client.go               # gcpRequest REST 封装 + GCP_API_BASE_URL 可覆盖
├── auth.go                 # SA JSON → JWT → access token + 内存 token 缓存
├── compute_service.go      # instances/zones/regions/machineTypes/images
├── project_service.go      # Resource Manager projects
└── service_test.go
```

规模超出单文件承载能力时按资源域继续拆分（storage_service.go、billing_service.go 等），禁止把所有逻辑堆进超大 `service.go`。

### 5. 路由与鉴权：Manifest 一行前缀 + AuthSession

- `manifest.go` 新增：`{Prefix: "/api/gcp", Module: "gcp", Owner: OwnerGo, Auth: AuthSession, ResponseMode: ResponseJSON, Description: "Google Cloud Platform accounts and resources"}`
- `server.go` 按新模块标准四处改动（import、Server 字段、newServer 实例化、serveGoRoute case）。
- 全部接口走 session auth，写操作（POST/PUT/DELETE）均为登录态用户操作。

### 6. 前端：独立 GcpPage，注册进 cloud-vendors 分组

- `src/js/pages/GcpPage.jsx`（按需可拆 `src/js/pages/gcp/` 目录，同 OpenAIPage 模式）
- `store.js` 的 `MODULE_CONFIG` + `MODULE_GROUPS` cloud-vendors subgroup 增加条目。
- `MainLayout.jsx` lazy import + `renderActivePage` case。
- UI 全部 Kumo 组件、中文文案，高风险动作走 `DeleteResource` 确认，遵循《新模块接入指南》全部 UI 约束。

### 7. 与现有模块的边界

1. **不并入 `server` 模块**：GCP 是云资源控制面，与主机纳管（Agent/SSH/Docker）职责不同，与 Oracle 决策一致。
2. **与模型网关 Vertex AI 上游（/api/openai 端点的 vertex 类型）互不干扰**：网关 Vertex 上游用 API key 走 `x-goog-api-key`，GCP 模块用 SA JWT OAuth，两套凭证、两个模块，共享的只有「Google Cloud」这个厂商域。
3. **不做多租户 RBAC**，模块内不建独立权限模型。
4. GCP 实例→`server` 模块导入为后续弱集成，不作为第一版前置条件。

### 8. 异步操作语义

GCP 实例操作（start/stop/reset/delete）都是异步 Operation。决策：

- 后端在执行动作后立即返回 Operation 信息（`name`、`status`、`targetLink`）。
- 前端展示「指令已下发」，通过列表刷新 + Operation 状态查询接口观察最终状态，不假定请求成功即资源已变更。
- 不实现长轮询/SSE 推送 Operation 进度（第一版靠手动刷新，与 Oracle 模块一致）。

### 9. 资源作用域与 zone 语义

GCP 多数 Compute 资源（instance、disk、address 等）是 zone/region 作用域资源：

- 列表统一走 `aggregatedList`（一次取全区域），返回 items 键含 `zones/{zone}/...` 前缀，需拆出 zone 与资源名两个字段。
- 单个资源的详情与操作必须携带 zone：`projects/{project}/zones/{zone}/instances/{instance}`，前端标识一个实例 = (account, project, zone, name)。
- 面板路由统一以 `?zone=` 查询参数承载 zone 上下文（不放路径段，避免与资源名歧义）。

## 后果

- 优点：零新增 Go 依赖（JWT 签名用标准库），模块轻量、可测、与现有架构完全一致；SA JSON 加密落库建立凭证安全基线。
- 缺点/代价：GCP REST 响应结构需要手写归一化层（Normalized* 结构），比 SDK 类型化成本高；后续若需接入 GCP 专有 gRPC-only API（目前无此需求）需重新评估。
- 风险与缓解：
  - SA JSON 泄露风险：secure 加密 + 列表脱敏 + 日志不打印私钥（同 Oracle 安全要求）。
  - Token 交换失败：错误信息需把 OAuth2 error 响应转成中文摘要 + 原始错误。
  - REST 分页（pageToken）：统一在 client 层处理，避免每处手写。
