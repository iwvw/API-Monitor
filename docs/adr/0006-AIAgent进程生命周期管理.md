# ADR-0006：AI Agent 进程生命周期管理

- 状态：已接受
- 日期：2026-09-21

## 背景

[ADR-0004](./0004-AIAgent管理模块架构决策.md) 第 41 条曾明确「不做 Agent 进程的启动/停止/重启管理（第一版只做探测与转发；进程生命周期后续评估）」。该决策在当时是合理的：进程管理会显著扩大安全面，且第一版的目标只是把已运行的 Agent 服务接上来。

实现期暴露了三个「只探测不管理」无法解决的问题：

1. **端口被占用即不可用**。`store.go` 把实例端口硬锁为 Provider 默认端口（OpenCode 为 4096），理由是「放开任意端口会把网关变成到主机任意本地服务的转发器」。但实际部署中 4096 常被其它进程或另一个 opencode 实例占用，此时既不能改端口，也没有让用户腾出端口的途径，实例只能长期处于离线。
2. **探测结果可能误报在线**。进程匹配与端口监听是两个独立判定，没有关联验证。当 4096 被 A 进程监听、而系统里另有 opencode 进程运行时，探测会报告 `online`，但它指向的并非同一个实例。多实例共存时无法区分。
3. **多端状态无单一事实来源**。实例的「期望是否运行」没有登记，云端只能反映「此刻探测到什么」。用户在手机上看到的状态与电脑上手工启动/停止进程后的状态无法收敛。

ADR-0004 原文留有演进余地（「进程生命周期后续评估」），本 ADR 即为该评估的结论。

## 决策

引入**进程生命周期管理**：云端登记实例的期望状态与端口，经既有控制通道下发任务，由主机 Agent 负责启动、停止与守护本地 Agent 进程。数据面通道（ADR-0005）不变。

### 1. 端口：Provider 默认端口 + 显式登记端口

放开「必须等于 Provider 默认端口」的硬约束，改为白名单：

1. 实例创建时端口可省略，省略则取 `Provider.DefaultPort`。
2. 显式指定端口时，必须落在**该 Provider 的允许端口区间**内（默认 `[DefaultPort, DefaultPort+99]`，可由 Provider 注册表覆盖）。
3. 端口仍是「本机回环上的 AI Agent 服务端口」，不是任意本地服务端口；网关只转发到 `127.0.0.1:<instance.Port>`。
4. 同一主机上，`(server_id, port)` 必须唯一，避免两个实例指向同一端口。

保留白名单而非完全放开，是为了不把网关变成任意本地服务的转发器——这正是原决策要防的风险，本 ADR 通过「区间约束 + 主机内端口唯一」而非「锁死单值」来达成同样目的。

### 2. 进程与端口关联验证

探测任务（类型 56）的返回值增加「监听该端口的 PID」，云端以它为主判定依据：

1. Agent 侧解析 `127.0.0.1:<port>` 的监听 PID（Windows 走 `GetExtendedTcpTable`，Linux 走 `/proc/net/tcp` + `inode` 反查）。
2. 云端判定 `online` 的条件收紧为：**监听 PID 存在，且该 PID 命中进程匹配规则**。
3. 若监听 PID 存在但进程名不匹配，报告为「端口被其它进程占用」，而不是 `online`。
4. 若进程匹配命中但无人监听该端口，报告为「进程已运行但未监听预期端口」。

这样消除了「A 进程占端口 + B 进程同名」导致的误报。

### 3. 期望状态与收敛

实例新增期望状态字段，云端按它收敛实际状态：

1. `desired_state`：`running` | `stopped`。管理员或用户显式设置。
2. Agent 侧维护自己启动的进程表（instanceID → PID + 端口 + 启动时间）。
3. 云端在实例列表/详情查询时，按需触发收敛：期望 `running` 但实际未运行 → 下发启动；期望 `stopped` 但实际在运行 → 下发停止。
4. 收敛是**幂等**的：重复下发同一期望状态不产生副作用。
5. 收敛失败不改变期望状态，只记录错误与时间，供 UI 展示「收敛失败」而非「已停止」。

### 4. Agent 侧进程守护

Agent 启动的进程由其自身守护：

1. 进程随 Agent 的 supervisor 管理，异常退出后按退避策略重启（1/2/5/10/30 秒，共 5 次；超过则标记 `crashed` 并上报）。
2. Agent 重启后**恢复**此前处于 `running` 期望的进程：进程表持久化到 Agent 本地状态文件，仍存活的条目保留，已死的条目保留 `desired_running` 并交由 supervisor 拉起。
3. Agent 主动退出（如被卸载/停止）时，终止其托管的所有进程，避免孤儿进程占用端口。
4. 显式 `stop` 会保留进程表条目但置 `desired_running=false`，supervisor 据此跳过——这是「用户停止」与「进程崩溃」的区别所在。`crashed` 的实例需显式 `start` 才能恢复。
5. supervisor 的巡检间隔为 500ms（亚秒级自愈），与云端 30 秒的收敛循环分工不同（见第 3.3 条）。

### 4.1 云端后台收敛

收敛不能只在「有人查看实例列表」时发生——否则进程崩溃且无人打开面板时永远不会被拉起。因此：

1. 云端启动一个 30 秒间隔的后台收敛循环，遍历全部 `desired_state != ""` 且启用的实例做收敛。
2. 与 Agent 侧 supervisor 的分工：supervisor 负责进程级崩溃自愈（亚秒级、主机本地）；云端收敛负责期望状态层面的纠偏（如 Agent 重启、配置变更后）。两者幂等，重复拉起不会产生重复进程。
3. 收敛循环由进程入口启动一次，自行持有可取消的 context，不挂在任何 HTTP 请求的生命周期上。

### 5. 任务类型与能力位

沿用既有一次性任务通道（`dashboard:task`），新增三个任务类型，避开已用的 1-56：

| 类型 | 名称 | 语义 |
| --- | --- | --- |
| 57 | `aiagent_start` | 启动指定 Provider 的本地服务，绑定给定端口 |
| 58 | `aiagent_stop` | 停止该实例对应的进程 |
| 59 | `aiagent_status` | 返回该实例的进程表条目（PID、端口、启动时间、运行时长、重启次数、内存、CPU） |

能力位新增 `aiagent_lifecycle_v1`。云端以 `requireAgentCapability` 门禁，缺失时返回明确的升级提示，而不是静默降级为「只探测」。

### 5.1 资源占用采集

探测（任务 56）与状态查询（任务 59）都返回目标进程的内存与 CPU：

1. 内存为常驻内存字节数，CPU 为相对单核的百分比。
2. 采集以「实际监听端口的进程」为准（与在线判定同源），没有监听者时退回进程匹配结果。
3. 用持久化的 `sysinfo::System` 实例做增量刷新：CPU 百分比依赖两次采样之间的时间差，每次新建实例单次刷新会恒返回 0。
4. 只刷新目标进程（`ProcessesToUpdate::Some`），不做全表扫描——探测是高频路径。

### 6. 安全约束（本决策的主要代价）

「可远程启动进程」比「只读探测」的安全面大得多，因此必须配套以下约束，缺一不可：

1. **二进制来源白名单**：Agent 只启动预置路径下的可执行文件，不接受云端传入任意路径。路径由 Agent 本地配置决定，云端只能指定 Provider ID。
2. **参数模板化**：云端不能传任意命令行参数；Agent 按 Provider 模板拼装（如 `opencode serve --hostname 127.0.0.1 --port <port>`），端口做数值范围校验。
3. **端口区间约束**：见第 1 条。
4. **审计**：每次 start/stop 落 `aiagent_access_logs`，含操作者、实例、结果。
5. **能力门禁**：仅 `aiagent_lifecycle_v1` 的 Agent 接受这三类任务；旧 Agent 明确报错而非忽略。

不采用「Agent 下载并执行云端提供的二进制」方案：`tcp_forwarder.rs` 已有该范式（含 SHA256 校验），但 AI Agent 的二进制应由用户在主机上自行安装与升级，云端不应成为其分发通道。

### 7. 与用户手工启动的实例共存

进程管理**不排斥**手工启动：

1. 手工启动的实例仍可登记，此时 `desired_state` 留空（不收敛），仅做探测与转发。
2. 一旦用户对某实例执行 start/stop，该实例转入托管模式，`desired_state` 被设置，此后由云端收敛。
3. 托管模式下若检测到端口被非托管进程占用，start 失败并明确报错，不静默杀掉他人进程。

### 8. 数据库仍为单一实例

本决策不引入独立数据目录：同一主机上的多个 opencode 进程共享同一个 SQLite（`~/.local/share/opencode/opencode.db`）。这是已知的、被接受的取舍——多实例的用途是「不同端口/不同工作目录的并行会话」，不是数据隔离。若未来需要数据隔离，需单独决策 `OPENCODE_DATA_DIR` 的注入方式。

## 后果

- 优点：端口冲突从「不可用」变为「可配置」；探测不再误报；多端共享同一份期望状态；进程崩溃可自愈。
- 缺点/代价：安全面显著扩大（远程启动进程）；需要改动 Rust Agent 并重新发布；Agent 需维护进程表与守护逻辑。
- 风险与缓解：
  - 云端被攻破后可远程启动进程 → 二进制白名单 + 参数模板化 + 端口区间 + 审计日志，云端无法指定任意路径或参数。
  - 守护逻辑导致进程反复重启 → 退避策略 + 重启次数上限 + `crashed` 终态上报。
  - Agent 崩溃留下孤儿进程 → Agent 退出时终止托管进程；Agent 重启后按进程表恢复或清理。
  - 收敛与用户手工操作冲突 → 仅对显式设置过 `desired_state` 的实例收敛；手工实例不收敛。
  - 旧 Agent 不支持新任务 → 能力位门禁 + 明确升级提示。
