# 定时任务与工作流调度 PRD

最后更新：2026-06-30

## Problem Statement

当前“定时任务”模块只覆盖基础 cron 任务 CRUD、手动运行和运行日志。它不足以支撑 API Monitor 后续的自动化场景：用户无法编排多个任务之间的依赖，无法用可视化方式理解复杂 cron 规则，无法在多节点环境中控制任务落点，也无法稳定追踪一次工作流运行中每个步骤的状态、输入输出和失败原因。

用户需要的是一个完整的自动化工作流调度器：既能处理简单定时任务，也能处理有依赖、有分支、有重试、有多节点执行位置的复杂运维自动化。

## Solution

将现有定时任务模块升级为“工作流调度”模块，保留简单任务体验，同时新增工作流编排、任务依赖 DAG、分布式调度和可视化 cron 编辑器。

模块仍以“定时任务”为入口名称，内部提供四个主视图：

1. 任务：管理可独立运行的单步任务。
2. 工作流：管理由多个节点组成的 DAG 编排。
3. 运行记录：查看任务和工作流实例的执行过程、日志、状态和输出。
4. 执行节点：查看本机与远端执行节点的健康、能力、并发和调度归属。

所有可见 UI 使用中文，基础 UI 优先使用 Kumo 组件和 token。

## User Stories

1. 作为管理员，我想创建一个每天固定时间运行的任务，以便自动执行重复维护操作。
2. 作为管理员，我想使用可视化 cron 编辑器选择周期，以便不用记忆 cron 语法。
3. 作为高级用户，我想直接输入 cron 表达式，以便配置复杂时间规则。
4. 作为管理员，我想在保存前看到下次若干次运行时间，以便确认周期配置正确。
5. 作为管理员，我想创建 Shell、HTTP、内部接口和 Agent 命令任务，以便覆盖本地与远程自动化场景。
6. 作为管理员，我想启用、停用、编辑、复制和删除任务，以便管理任务生命周期。
7. 作为管理员，我想立即运行任务，以便验证任务配置是否可用。
8. 作为管理员，我想查看任务下次运行时间、上次运行时间和最近结果，以便判断任务是否健康。
9. 作为管理员，我想设置任务超时、重试次数和重试间隔，以便处理短暂网络或服务抖动。
10. 作为管理员，我想限制任务最大并发，以便避免同一任务重复运行造成资源冲突。
11. 作为管理员，我想选择任务运行位置，以便让任务在本机或指定 Agent 节点执行。
12. 作为管理员，我想设置节点标签和任务标签选择器，以便让任务自动调度到合适节点。
13. 作为管理员，我想看到执行节点在线状态、最近心跳、版本、并发容量和当前负载，以便排查分布式调度问题。
14. 作为管理员，我想把多个任务拖拽编排成工作流，以便表达先后顺序和依赖关系。
15. 作为管理员，我想让某个任务成功后再运行下游任务，以便自动完成多步流程。
16. 作为管理员，我想让某个任务失败后运行补偿任务或通知任务，以便自动处理异常。
17. 作为管理员，我想在 DAG 中阻止环形依赖，以便保证工作流可执行。
18. 作为管理员，我想复制已有工作流，以便快速创建相似自动化流程。
19. 作为管理员，我想禁用工作流中的某个节点，以便临时绕过某一步。
20. 作为管理员，我想手动触发工作流，以便在不等待定时触发的情况下验证流程。
21. 作为管理员，我想查看一次工作流运行的 DAG 状态图，以便知道卡在哪个节点。
22. 作为管理员，我想查看每个节点的输入、输出、开始时间、结束时间、耗时和日志，以便定位失败原因。
23. 作为管理员，我想重新运行失败节点或从失败节点继续运行，以便不用重跑整个流程。
24. 作为管理员，我想取消正在运行的任务或工作流，以便停止错误操作。
25. 作为管理员，我想清理旧运行记录，以便控制数据库体积。
26. 作为管理员，我想清空全部运行记录时看到明确确认，以便避免误删审计信息。
27. 作为管理员，我想把工作流运行结果发送到通知模块，以便及时知道关键自动化失败。
28. 作为管理员，我想搜索、筛选和分页任务与运行记录，以便在任务数量变多后仍能快速定位。
29. 作为管理员，我想导出或导入工作流定义，以便备份和迁移自动化配置。
30. 作为管理员，我想所有操作都有明确中文反馈，以便减少误解。

## Functional Requirements

### 任务管理

- 支持任务类型：Shell 命令、HTTP 请求、内部接口、Agent 命令。
- 支持任务字段：名称、描述、类型、执行内容、启用状态、调度类型、执行节点策略、超时、重试、最大并发、标签。
- 支持调度类型：手动、Cron、一次性时间、工作流依赖触发。
- 保存任务时校验必填字段、cron 表达式、URL、内部路径、超时范围和并发范围。
- 任务列表展示启用状态、运行状态、任务类型、调度摘要、执行位置、下次运行、最近结果。

### 可视化 Cron 编辑器

- 支持每分钟、每小时、每天、每周、每月、自定义表达式。
- 支持高级 cron 输入和实时语法校验。
- 支持预览未来 5 次运行时间。
- 支持显示自然语言摘要，例如“每天 03:30 执行”。
- 前后端都必须校验 cron 表达式，非法表达式不可保存。

### 工作流编排

- 工作流由多个节点和边组成，节点引用任务定义或内联任务配置。
- 边支持依赖条件：成功后、失败后、完成后。
- 工作流必须是 DAG，保存时校验无环、无孤立非法入口、无缺失任务引用。
- 支持开始节点、结束节点、普通任务节点、条件节点、通知节点。
- 支持节点级超时、重试、启用状态、执行节点策略覆盖。
- 支持工作流级启用状态、调度规则、并发策略和失败策略。

### DAG 可视化

- 提供可视化编辑画布，支持新增节点、连接依赖、删除边、移动节点。
- 节点显示名称、类型、状态、最近结果。
- 保存前展示校验错误。
- 运行详情中复用 DAG 视图展示每个节点实例状态。
- 画布实现可使用轻量 SVG/HTML 自研，优先保持可测试的数据模型；复杂交互不可阻塞核心调度能力。

### 分布式调度

- 本机后端作为调度控制面，执行节点包括 local 和已注册的 Agent。
- 节点有唯一 ID、名称、地址、标签、能力、最大并发、心跳时间、在线状态。
- 任务可选择 local、指定节点、标签匹配或自动选择。
- 调度器必须处理节点离线、节点并发满、任务超时和运行中断。
- 同一任务或工作流的并发策略支持：允许并发、跳过新实例、排队等待。
- 分布式执行的第一版以现有 server agent 能力为基础，不新增独立外部调度服务。

### 运行记录与日志

- 区分任务运行实例、工作流运行实例、节点运行实例。
- 状态包括：排队中、运行中、成功、失败、已取消、已跳过、超时。
- 日志列表展示状态、对象名称、触发方式、开始时间、耗时、执行节点、摘要。
- 详情弹窗展示完整输出、错误、HTTP 状态码、节点信息和重试历史。
- 支持按任务、工作流、状态、时间范围筛选。
- 支持清理 N 天前记录和清空全部记录，清空全部必须二次确认。

## Implementation Decisions

- 保留现有 `/api/cron` 作为兼容入口，但后端领域模型升级为 scheduler/workflow。
- 数据模型从单表任务和日志扩展为任务定义、工作流定义、工作流节点、工作流边、运行实例、节点实例、执行节点。
- 调度内核抽成可测试深模块，输入任务/工作流定义和当前节点状态，输出可执行的运行计划。
- DAG 校验抽成纯函数模块，负责无环检测、入口检测、引用检测和依赖条件校验。
- Cron 解析与未来运行时间预览抽成纯函数模块，前端展示结果以后端校验为准。
- 执行器按任务类型拆分 Shell、HTTP、Internal、Agent，统一返回结构化结果。
- 前端任务、工作流、运行记录和执行节点共用状态 Badge、详情 Dialog、Empty、Table 模式。
- UI 基础组件遵守 Kumo 迁移规则，不新增通用自写 Button/Input/Dialog/Table/Switch。
- 内部模块 key 与路由统一为 `scheduler`，旧 `/self-h` 仅作为兼容跳转入口。

## Testing Decisions

- 后端单测优先覆盖调度内核、DAG 校验、cron 校验和执行器结果归一化。
- API 测试覆盖任务 CRUD、非法 cron 拒绝、工作流保存校验、手动运行、取消、日志清理。
- 前端测试覆盖 cron 表达式生成/解析、DAG 数据校验、列表状态渲染和中文文案。
- 浏览器烟测覆盖空态、新建任务、任务列表、工作流画布、运行详情、窄屏布局。
- 验证命令至少包括 `npm run lint -- --quiet`、`npm run test`、`npm run build`、`npm run backend-go:test`。

## Release Plan

虽然目标是一次性完成完整模块，但实现必须按可验证纵切面推进：

1. 数据模型与兼容 API：保留现有 cron 能力并迁移到新模型。
2. 单任务调度增强：cron 校验、next run、重试、超时、并发策略。
3. 运行记录增强：结构化日志、详情弹窗、筛选和清理。
4. 工作流 DAG 模型：定义、校验、保存、手动运行。
5. 工作流执行器：依赖调度、失败策略、节点状态和重试。
6. 分布式节点：local/agent 节点注册、心跳、标签调度、并发控制。
7. 可视化编辑器：cron 编辑器和 DAG 编辑画布。
8. 全量联调与浏览器验收。

每个纵切面必须保持主分支可构建、可测试、可回退。

## Acceptance Criteria

- 侧边栏、面包屑和页面标题均显示“定时任务”。
- 用户可以创建简单任务并看到未来运行时间。
- 用户可以使用可视化 cron 编辑器并预览未来 5 次运行。
- 非法 cron 在前后端都不能保存。
- 用户可以创建包含至少 3 个节点和成功依赖的工作流。
- 系统拒绝保存环形依赖工作流。
- 用户可以手动运行工作流，并在 DAG 视图中看到节点状态变化。
- 失败节点可以查看错误、输出和重试历史。
- 用户可以将任务调度到 local 或指定 Agent 节点。
- 节点离线时任务不会无声失败，运行记录必须显示明确原因。
- 日志详情不会把大段 HTML 或输出直接撑爆列表。
- 清空全部运行记录有明确二次确认。
- 页面所有可见 UI 为中文。
- Kumo 静态基线扫描无新增违规。
- `npm run lint -- --quiet`、`npm run test`、`npm run build`、`npm run backend-go:test` 通过。

## Out of Scope

- 不接入外部 Kubernetes/Celery/Temporal/Argo 等独立调度平台。
- 不实现多租户权限隔离。
- 不实现复杂表达式语言或脚本沙箱。
- 不承诺跨多台控制面高可用；第一版控制面仍为 API Monitor 主后端。
- 不把 DAG 编辑器做成通用低代码平台。

## Further Notes

- 分布式调度要优先复用现有 Rust Agent / server agent 通道，避免引入第四套运行时。
- DAG 编辑器的体验重要，但核心正确性应由后端 DAG 校验和执行状态机保证。
- 旧 `/api/cron` 可以作为兼容层保留一段时间，前端完成迁移后再决定是否废弃。
