# 语义化表格布局与移动端适配 PRD

状态：已实施（核心标准已落地并全站铺开）  
最后更新：2026-09-08  
目标版本：已完成  
适用范围：API Monitor 前端所有 Kumo 数据表格  
依赖：`@cloudflare/kumo` 2.8 或兼容版本（当前 2.13.1）

实施情况（2026-09-08）：核心标准由 `src/js/components/ui/AppPrimitives.jsx` 的 `AppTable` + `resolveTableColumns` 实现（语义列角色 `primary/status/number/datetime/meta/actions-*`、自动 `colgroup`、`minWidth/grow`、开发期警告），已用于华为云/GCP/Oracle/腾讯云/M365/订阅/备份等页面。剩余治理项见仓库内用例与后续审计。

## Problem Statement

API Monitor 当前已经统一使用 Kumo `Table` 作为表格基础组件，但列宽仍主要由各页面自行决定。不同页面分别使用浏览器自动布局、固定布局、手写 `colgroup`、像素数组、百分比数组和可拖动宽度，缺少一套跨模块共享的设计标准。

现状造成以下用户问题：

- 固定布局缺少有效 `colgroup` 时，名称、状态、时间和操作列被平均分配，短字段过宽、主内容列过窄。
- 部分宽度数组只改变表格最小宽度，并未真正控制对应列宽，代码表达与浏览器结果不一致。
- 百分比列宽在宽屏下同比放大复选框、状态、时间和操作列，浪费横向空间。
- 长 URL、ID、按钮组或 `whitespace-nowrap` 内容可以反向撑宽自动布局表格。
- 单行和多行内容混合时，操作、选择和状态单元格可能按基线对齐，无法稳定垂直居中。
- 移动端缺少统一策略：有些表格被压缩至不可读，有些产生页面级横向溢出，有些隐藏信息但没有替代入口。
- 同类字段在不同模块的宽度、对齐和截断方式不同，增加视觉噪声和维护成本。

Kumo 当前提供 `auto/fixed` 布局、语义化表格元素、选择列、sticky 列和 ResizeHandle，但不提供业务语义列角色、宽度上下界、移动端优先级或应用级列宽治理。因此需要在 Kumo 之上增加一个窄而稳定的业务组合层，而不是替换 Kumo Table。

## Solution

建立 API Monitor 统一的“语义化表格布局标准”。页面用列角色描述业务意图，公共布局模块将其解析为 Kumo Table 所需的 `colgroup`、表格最小宽度、水平和垂直对齐、截断策略、移动端可见性和可选 sticky 行为。

该标准采用以下核心原则：

1. 工具列保持稳定，多个有阅读价值的内容列共同吸收剩余空间。
2. 每个列角色同时定义最小宽度、理想宽度和允许的增长行为，避免过窄或无意义地过宽。
3. 业务表默认使用固定布局；仅简单、短内容表格允许自动布局。
4. 操作、选择、状态、开关和数值列默认垂直居中。
5. 移动端保持可读宽度，溢出限制在表格容器内部，不通过压缩所有列来强行适配屏幕。
6. 辅助列只有在信息存在替代入口时才能响应式隐藏。
7. 页面仍然直接组合 Kumo `Table.Head`、`Table.Cell`、`Table.CheckHead`、`Table.CheckCell` 和 `Table.ResizeHandle`，公共层只负责业务布局，不创建新的基础 Table 实现。

## Goals

- 为所有业务表格提供一套可复用、可测试、可审计的列宽标准。
- 消除固定表格平均分列、宽度数组失效和工具列同比放大的问题。
- 统一操作列及其他工具列的水平、垂直对齐。
- 在桌面、平板和移动端保持相同的信息层级与可读性原则。
- 支持现有可拖动表格，并为后续宽度持久化保留扩展点。
- 允许业务页面做少量、显式、有边界的宽度覆盖。
- 通过渐进迁移完成改造，不要求一次性重写所有业务表格。

## Column Role Standard

列规格采用语义角色，而不是裸宽度数组。默认值是设计基线，业务可以在合理范围内覆盖。

| 角色 | 最小宽度 | 理想宽度 | 默认增长 | 水平对齐 | 垂直对齐 | 典型内容 |
| --- | ---: | ---: | --- | --- | --- | --- |
| `check` | 40px | 40px | 不增长 | 居中 | 居中 | Kumo 选择框 |
| `control` | 48px | 56px | 不增长 | 居中 | 居中 | 开关、启停按钮 |
| `status` | 72px | 88px | 不增长 | 居中 | 居中 | 状态 Badge |
| `type` | 80px | 96px | 不增长 | 居中 | 居中 | 类型、协议、环境 |
| `count` | 72px | 88px | 不增长 | 右对齐 | 居中 | 数量、次数 |
| `number` | 88px | 112px | 不增长 | 右对齐 | 居中 | 大小、余额、延迟 |
| `date` | 104px | 120px | 不增长 | 左对齐 | 居中 | 简短日期 |
| `datetime` | 136px | 160px | 不增长 | 左对齐 | 居中 | 完整日期时间 |
| `meta` | 104px | 136px | 默认不增长 | 左对齐 | 居中 | 地域、版本、短标识 |
| `actions-sm` | 56px | 72px | 不增长 | 居中 | 居中 | 单个图标操作 |
| `actions-md` | 96px | 120px | 不增长 | 居中 | 居中 | 两个紧凑操作 |
| `actions-lg` | 144px | 184px | 不增长 | 居中 | 居中 | 三个操作或文字按钮 |
| `actions-xl` | 280px | 340px | 不增长 | 居中 | 居中 | 必须单行展示的三个文字操作 |
| `primary` | 160px | 240px | 优先增长 | 左对齐 | 居中 | 名称、标题、主要对象 |
| `content` | 200px | 320px | 优先增长 | 左对齐 | 顶部或居中 | URL、地址、描述、组合信息 |
| `identifier` | 176px | 240px | 可增长 | 左对齐 | 居中 | ID、Token 摘要、邮箱 |

补充规则：

- 一个表格通常应至少包含一个 `primary`、`content` 或 `identifier` 弹性列。
- 宽表优先声明多个弹性内容列共同分配余量；固定工具列不得参与剩余空间同比放大。
- “最大宽度”主要约束列内可读内容，而非强制表格留下空白；全宽表格的剩余空间仍由弹性列承接。
- 弹性列内容达到可读上限后，通过内部 `max-width`、截断、Tooltip、ClipboardText 或详情入口控制阅读长度。
- 业务覆盖不得低于角色最小宽度；超过建议上限时必须说明内容或操作需求。
- 操作列宽度按实际可见操作数量和按钮形式选择，不按页面宽度同比缩放。

## Alignment Standard

### Vertical alignment

- 业务表体单元格默认 `vertical-align: middle`。
- `check`、`control`、`status`、`type`、`count`、`number` 和所有 `actions-*` 角色强制垂直居中。
- `content` 列在明确包含多行描述、日志或堆叠字段时可以声明顶部对齐。
- 同一行存在两行主内容时，操作按钮仍应与整行视觉中心对齐，而不是与第一行文本基线对齐。
- 表头默认垂直居中；可拖动手柄必须覆盖完整表头高度并保持可点击区域。

### Horizontal alignment

- 主内容、描述、标识和时间默认左对齐。
- 状态、类型、选择、开关和操作默认居中。
- 数量、金额、容量、延迟等可比较数值默认右对齐并使用 tabular numbers。
- 表头与对应表体单元格必须使用相同的水平轴，不允许只给表头添加对齐类。

## Desktop and Wide-screen Standard

- 表格默认填满所在数据面板，但仅弹性列吸收额外宽度。
- 固定工具列在 1024px、1440px 和更宽视口下保持理想宽度，不随表格宽度同比增长。
- 当所有业务列都是固定角色时，必须指定一个列作为弹性主列，或明确使用内容适配表格。
- 数据密集表格可以设置表格最小宽度并在自身容器横向滚动。
- sticky 操作列只用于确实需要横向滚动且操作需要持续可见的表格。
- sticky 列必须使用 Kumo 提供的 sticky 能力，保持不透明背景、层级和边缘渐变。
- 可拖动列宽应遵守每个角色的最小/最大限制，禁止把状态或操作列拖到不可用宽度。

## Mobile and Tablet Standard

移动端沿用同一列角色和宽度边界，不维护另一套互相冲突的数字。

### Baseline behavior

- 360px 至 767px 视口下，不把所有列压缩到一屏。
- 表格最小宽度由可见列的角色最小宽度计算，超出视口时仅表格框架横向滚动。
- 页面、主内容和卡片不得产生页面级横向滚动。
- 表头与首行不得因滚动容器或 sticky 列发生错位。
- 横向滚动区域使用 overscroll containment 和触摸横向手势支持。

### Responsive priority

每列可以声明以下优先级：

- `essential`：始终显示，例如选择、状态、主名称和关键操作。
- `supporting`：平板显示；移动端只有在信息同时合并到主列或详情入口时才可隐藏。
- `optional`：可在较窄视口隐藏，但必须保证用户仍能在详情、Tooltip、展开区或复制入口取得信息。

禁止仅为了避免横向滚动而静默丢失唯一信息。

### Mobile actions

- 单个主要操作使用 Kumo 图标按钮并提供明确 `aria-label`。
- 多个低频操作优先收敛到 Kumo Dropdown；危险操作仍使用明确语义和确认流程。
- 需要持续可见时，紧凑操作列可以 sticky 到右侧；包含宽文字按钮组时不默认 sticky。
- 操作控件的实际触摸目标不得小于 44px，即使视觉图标更小。
- 操作列必须垂直居中，不因主列两行或三行内容漂到顶部。

### Mobile content

- 主名称保持单行截断，次要信息可在同一主单元格中以第二行呈现。
- URL、ID 和地址默认不完整换行撑高整行；使用截断、复制或详情入口。
- 不允许通过缩小到难以阅读的字体来容纳列。
- 当移动端表格仍无法高效使用时，可以采用业务专用列表或详情卡片，但必须作为显式产品决策，不由通用布局层自动把 table 改成 card。

## User Stories

1. 作为桌面端用户，我希望名称和描述获得主要横向空间，以便快速识别数据对象。
2. 作为桌面端用户，我希望状态、时间和操作列保持稳定宽度，以便跨行快速扫描。
3. 作为宽屏用户，我希望额外空间用于主要内容，而不是把复选框和操作列无限放大。
4. 作为窄屏用户，我希望表格保持可读列宽，以便内容不会挤成难以辨认的碎片。
5. 作为移动端用户，我希望横向滚动只发生在表格内部，以便整页导航和返回手势不受影响。
6. 作为移动端用户，我希望关键状态、名称和操作始终可访问，以便不需要切换到桌面端完成管理任务。
7. 作为移动端用户，我希望被隐藏的辅助信息仍能在详情或主单元格中找到，以便不会静默丢失数据。
8. 作为触屏用户，我希望操作按钮拥有足够大的点击区域，以便减少误触。
9. 作为键盘和辅助技术用户，我希望表格继续使用语义化 table、header 和 cell，以便正确理解行列关系。
10. 作为用户，我希望多行内容所在行的操作按钮垂直居中，以便每行保持清晰的视觉关联。
11. 作为用户，我希望数量、金额和容量右对齐，以便更容易纵向比较数值。
12. 作为用户，我希望长 URL、ID 和描述以一致方式截断并可查看完整值，以便表格不会被极端内容撑坏。
13. 作为管理员，我希望数据密集表格可以安全调整列宽，以便适配当前工作重点。
14. 作为管理员，我希望调整列宽时存在最小边界，以便不会把列拖到无法恢复或无法操作。
15. 作为前端开发者，我希望使用语义列角色而不是记忆像素数组，以便不同模块自然保持一致。
16. 作为前端开发者，我希望公共层自动生成正确的 `colgroup`，以便声明的宽度确实反映在浏览器中。
17. 作为前端开发者，我希望可以对特殊业务列做有限覆盖，以便标准不会阻止真实需求。
18. 作为前端开发者，我希望列规格同时产生宽度和对齐行为，以便表头与表体不会分别维护样式。
19. 作为前端开发者，我希望移动端隐藏规则由列规格表达，以便表头和所有单元格始终同步。
20. 作为维护者，我希望新增表格违反标准时在开发或 CI 阶段被发现，以便避免重新引入平均分列。
21. 作为维护者，我希望现有表格能够分批迁移，以便控制大型页面的回归风险。
22. 作为维护者，我希望共享宽度算法具有独立测试，以便修改设计 token 时能预测全局影响。
23. 作为维护者，我希望代表性表格在多个视口接受浏览器验证，以便发现 CSS 和真实布局算法差异。
24. 作为设计维护者，我希望能够集中修改某类列的理想宽度，以便统一改善所有模块。
25. 作为设计维护者，我希望 Kumo 后续增加能力时可以替换本地解析实现，而无需修改每个业务页面。

## Implementation Decisions

### Semantic column specification

- 引入共享列规格模型，至少包含列标识、语义角色、可选宽度覆盖、增长权重、水平对齐、垂直对齐、响应式优先级、sticky 和是否允许拖动。
- 角色 token 集中维护，业务页面不得复制默认宽度数字。
- 宽度覆盖经过边界归一化；低于角色最小值时回退到最小值，并在开发环境给出可定位警告。
- 弹性列不写固定像素宽度；固定列写入 `colgroup`。
- 表格最小宽度根据固定列理想宽度与弹性列最小宽度计算。
- 第一阶段由多个弹性列均衡分配剩余空间；后续只有出现明确业务证据时才引入自定义增长权重，避免构建通用网格引擎。

### Deep layout module

- 建立纯函数列规格解析器，输入列规格和响应式上下文，输出归一化列定义、表格最小宽度、列样式和开发期诊断。
- 解析器不依赖 React、DOM 或具体页面数据，可以独立测试。
- 解析器是整个功能的深模块；宽度 token、边界、角色默认对齐和响应式规则只能在该模块内解释。

### Kumo composition layer

- 扩展现有应用表格组合层，而不是创建替代 Kumo 的基础 Table。
- 组合层继续渲染 Kumo `Table` 及其子组件，并自动渲染 `colgroup`。
- 组合层统一应用表体垂直居中；角色级覆盖通过列规格生成。
- 保留显式 `colgroup` 的过渡兼容能力，但不得同时提供语义列规格和手写列宽。
- 逐步弃用裸 `widths` 和无边界的百分比宽度模式。
- 开发环境验证列规格数量、表头数量和数据单元格数量，错误时提供表格标识和列标识。

### Responsive behavior

- 使用同一列规格生成桌面和平板/移动端行为。
- 列隐藏通过稳定列标识同步作用于 `col`、header 和 body cell。
- 通用层只执行声明的优先级，不自动猜测哪些业务信息可以隐藏。
- 页面需要在隐藏 supporting/optional 列时提供替代信息位置，并在迁移评审中验证。
- 横向滚动由统一数据表格框架承担；表格本身不得把 overflow 传播到页面。

### Alignment and actions

- 表体默认垂直居中；多行内容列可以声明顶部对齐。
- 操作列角色同时控制表头、单元格、按钮容器的水平和垂直对齐。
- 操作列不再依赖仅修改最后一列的全局选择器作为主要契约。
- 操作列宽度由角色或显式操作密度决定，不根据容器百分比增长。
- sticky 操作列使用 Kumo sticky API，不自行复制渐变和层级 CSS。

### Resizable tables

- ResizeHandle 继续使用 Kumo 组件。
- 拖动逻辑消费归一化列边界，遵守最小和可选最大宽度。
- 用户拖动后的像素宽度优先于角色理想值，但不改变角色的对齐和响应式优先级。
- 首期不要求跨设备同步宽度；本地持久化作为后续可选增强。

### Governance

- 增加静态检查或治理规则，识别固定布局却没有语义列规格/有效 `colgroup` 的表格。
- 标记新的裸百分比列宽、固定表格平均分列和未约束宽度数组。
- 允许少量经过文档说明的简单自动布局表格。
- 更新 Kumo UI 规则和前端最佳实践，使语义列规格成为新增业务表格默认标准。

## Migration Plan

### Phase 0 — Baseline inventory

- 生成现有表格清单，记录页面、列标题、布局模式、实际 `colgroup`、最小宽度、滚动容器和移动端表现。
- 标记高风险表格：固定布局无有效列宽、宽度数组未生效、工具列百分比增长、操作列按钮溢出、页面级横向滚动。
- 选定一张正确参考表、一张失效宽度表、一张移动端密集表和一张可拖动表作为回归样本。

### Phase 1 — Core standard and resolver

- 实现列角色 token 和纯函数解析器。
- 扩展 Kumo 组合层，自动生成 `colgroup`、最小宽度和角色对齐。
- 加入开发期列数量与冲突配置诊断。
- 为旧 `widths` 和百分比模式保留短期兼容，并发出弃用提示。

### Phase 2 — Representative migrations

- 迁移固定布局但宽度未真正生效的云厂商和 Microsoft 365 表格。
- 迁移备份、订阅日志和其他明显平均分列的表格。
- 迁移一张包含多行主内容和操作按钮的表格，确认垂直居中契约。
- 迁移一张移动端宽表，验证内部滚动、sticky 操作和响应式优先级。
- 根据真实数据调整角色 token，但不在页面层重新散落数字。

### Phase 3 — Full table migration

- 按模块逐批迁移剩余业务表格。
- 优先处理高流量页面和高风险巨型页面，保持每批改动可独立验证。
- 对明确适合自动布局的简单表格登记原因，不强制迁移到固定布局。
- 移除页面层重复的操作列对齐、百分比权重和无效宽度声明。

### Phase 4 — Governance and documentation

- 启用静态治理检查，阻止新增不符合标准的固定表格。
- 更新 UI 规则、开发最佳实践和新模块接入指南。
- 在完整迁移后移除旧宽度 API 和兼容警告。
- 记录仍需保留的业务例外及其退出条件。

## Testing Decisions

### Test philosophy

- 测试外部可观察行为，不断言内部函数拆分或具体 class 字符串。
- 宽度测试关注解析后的列边界、浏览器实际尺寸、溢出范围和信息可访问性。
- 不使用只验证“组件成功渲染”的浅层测试代替真实布局验证。
- 纯算法在单元测试中穷举边界；CSS 布局和响应式行为在真实浏览器中验证。

### Resolver unit tests

- 每个语义角色产生正确的最小宽度、理想宽度、增长行为和默认对齐。
- 业务覆盖不会突破最小边界。
- 固定列不参与弹性增长。
- 多个弹性列均衡分配剩余空间，避免单个主列在宽屏下形成大面积空白。
- 移动端优先级产生一致的可见列集合。
- supporting/optional 列缺少替代信息声明时产生开发期诊断。
- 操作密度映射到正确的操作列角色。
- 可拖动宽度受到最小和最大边界约束。

### Composition behavior tests

- 语义列规格生成与列数量一致的 `colgroup`。
- 表头和表体获得一致的水平与垂直对齐。
- 操作列默认垂直和水平居中。
- 显式 `colgroup` 与语义列规格冲突时给出明确错误。
- 表格最小宽度作用于表格框架内部，不造成页面级横向溢出。
- Kumo CheckHead/CheckCell、sticky 和 ResizeHandle 能力保持可用。

### Browser layout tests

代表性表格至少在以下视口验证：

- 360 × 800：窄移动端。
- 768 × 1024：平板或宽移动端。
- 1440 × 900：桌面宽屏。

浏览器验收包括：

- 固定工具列在不同桌面宽度下保持设计宽度，容差不超过 2px。
- 任意可见列不低于其角色最小宽度。
- 操作控件视觉中心与所在行中心偏差不超过 2px。
- 页面根没有横向溢出；需要的横向滚动只出现在表格框架。
- sticky 操作列滚动时不透明、无遮挡、表头与表体对齐。
- 隐藏列的信息可以通过声明的替代入口访问。
- 触摸操作目标不小于 44px。
- 键盘焦点、屏幕阅读器表头关系和操作 `aria-label` 保持有效。

### Regression commands

- 运行前端 lint、单元测试、UI governance 和生产构建。
- 涉及高风险页面时执行对应模块的浏览器冒烟验证。
- 完成全量迁移后执行完整前端审计，并保留迁移前后代表性列宽测量结果。

## Acceptance Criteria

1. 新增业务表格可以仅通过语义列规格获得一致列宽和对齐，不需要手写宽度数组。
2. 固定布局表格不会在缺少明确设计的情况下平均分列。
3. 复选框、状态、时间和操作等固定列在宽屏下不同比放大。
4. 主内容列获得剩余空间，并且不会低于声明的最小可读宽度。
5. 操作、选择、状态和控制列在单行及多行数据中稳定垂直居中。
6. 数值列、操作列和内容列遵守统一水平对齐标准。
7. 360px 移动端不存在由表格引起的页面级横向滚动。
8. 移动端关键列和关键操作始终可访问。
9. 响应式隐藏的任何信息都有经过验证的替代入口。
10. 代表性表格通过 360、768 和 1440 三类视口的浏览器布局测试。
11. 现有可拖动表格在迁移后继续工作并遵守最小宽度。
12. 治理检查能够阻止新的无约束固定表格和百分比工具列。
13. Kumo Table 仍是唯一基础表格组件，本地代码只承担业务组合和布局解析。
14. 所有高风险表格迁移完成后，旧宽度 API 可以安全移除。

## Risks and Mitigations

- 风险：一次性迁移大量页面造成视觉回归。缓解：按代表性表格、模块批次和高风险页面顺序渐进迁移。
- 风险：角色 token 无法覆盖全部业务内容。缓解：允许有边界的显式覆盖，并通过实际数据校准 token。
- 风险：响应式隐藏导致信息丢失。缓解：没有替代入口的列禁止隐藏，并增加开发期诊断与浏览器验收。
- 风险：sticky 操作列遮挡过多内容。缓解：仅对紧凑操作列启用，宽按钮组保持普通滚动列。
- 风险：列宽拖动与响应式规则冲突。缓解：用户宽度只覆盖理想值，不覆盖角色最小值和可见性规则。
- 风险：全局默认垂直居中影响日志或多行描述。缓解：内容角色可显式声明顶部对齐。
- 风险：Kumo 后续修改 Table DOM 或样式。缓解：保持组合层窄小，使用公开 Kumo API，并以浏览器行为测试锁定契约。

## Out of Scope

- 替换 Kumo Table 或引入另一套数据网格组件。
- 在首期实现排序、筛选、分页、虚拟滚动或列拖拽排序。
- 自动把所有移动端表格转换为卡片。
- 自动推断业务信息是否可以隐藏。
- 首期实现服务端或跨设备列宽同步。
- 重构与列宽、对齐和响应式无关的页面业务逻辑。
- 同时修复侧栏菜单点击区域重叠问题；该问题应独立跟踪。

## Further Notes

- 当前源码审计显示业务表格大量使用固定布局，但列宽表达方式不统一；共享组合层是最小且收益最高的改造入口。
- 模型网关中“主内容列吸收剩余空间、其他列固定”的表格可作为桌面布局参考。
- 订阅实例表可作为百分比工具列在宽屏下增长的回归样本。
- 备份表和订阅访问日志可作为固定布局平均分列的回归样本。
- PRD 通过后，建议先完成 Phase 0 和 Phase 1，再为各业务模块拆分独立、可回滚的迁移任务。
