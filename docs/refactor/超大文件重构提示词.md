# API Monitor 超大文件重构作战计划（AI 执行提示词）

> 用法：把本文件全文作为一条消息交给 AI（允许它使用子代理并行工作）。本文件是自包含的，AI 无需额外追问即可执行。
> 目标仓库：`E:\Code\API-Monitor`。
> **工作分支：`refactor/large-files`（从 `dev` 切出）。`dev` 与 `main` 受保护，重构期间只读不写。**

## 0. 角色与总目标

你是一名负责重构的技术负责人。本仓库存在大量超大文件（前端 24 个页面 >1000 行，其中 5 个 >3000 行；后端 7 个服务 >3000 行，最大 5457 行）。

你的目标：在**不改变任何对外行为**的前提下，把这些超大文件按职责拆分为多个小文件，使代码可导航、可维护、可被 AI 稳定修改。

这是一次**机械拆分重构**，不是功能改造。**严禁改变任何运行时行为、接口契约、路由、数据结构、UI 表现。**

**唯一验收标准：拆分后整个系统的可观测行为，与拆分前逐项一致（见第 6 节基线快照对比）。任何一处不一致都视为重构失败，必须回退。**

## 1. 绝对硬约束（违反即失败）

### 1.0 分支保护与工作流（第一优先级，开工前必须完成）

1. **开工前先切分支**：从最新的 `dev` 切出专用重构分支：
   ```bash
   git checkout dev
   git pull origin dev
   git checkout -b refactor/large-files
   ```
2. **`dev` 与 `main` 全程只读**：重构期间**禁止**在 `dev` 或 `main` 上提交、推送、合并、变基或强推。所有改动只发生在 `refactor/large-files`。
3. **禁止 `git push --force`**，禁止改写已推送历史。
4. **合入需人工确认**：重构全部完成、门禁全绿、基线快照零差异后，**停下来报告并等待人工确认**，由人工（或指定的单一集成窗口）执行合并：
   ```bash
   git checkout dev && git merge --no-ff refactor/large-files
   ```
   AI **不得**自行合并回 `dev`，更不得推送 `main`。
5. **工作区检查**：开工前运行 `git status`。若存在他人未提交的改动，**立即停止并报告**，不得在其上叠加。
6. **每批提交只提交本批次文件**，不得夹带无关改动；提交信息注明批次。

### 1.1 不可触碰的规则
1. **行为零变更**：拆分只做"搬移 + 重新组织导入导出"。不得重命名导出符号（除非仅调整文件路径）、不得改变函数签名、不得合并/拆分逻辑分支、不得"顺手修复"任何 bug、不得改任何字符串文案。
2. **禁止格式化整文件**：拆分过程中不得对未移动的代码做 reindent / 重排。每个新文件只包含搬移过去的内容，缩进层级保持原样。
3. **不碰运行时数据与密钥**：`data/`、`backup/`、`backend-go/data/`、`backend-go/internal/server/data/`、`.env`、`node_modules/`、`public/`、`src/pwa-public/vendor/`（drawio 第三方库，完全排除）一律不动。
4. **不改路由治理**：任何后端路由变更都必须在 `backend-go/internal/manifest/manifest.go` 登记。本次拆分**不应产生任何路由变更**；如拆分中发现不可避免要动路由，立即停止并报告，不要擅自改。
5. **不改数据库**：不得新增/修改 migration、schema、SQL。SQLite 结构完全不动。
6. **不引入新依赖**：`package.json` / `go.mod` 不得新增依赖。只允许使用仓库已有的库。
7. **不动测试语义**：测试可以跟随代码搬移而调整 import 路径，但**不得修改任何断言、不得删除测试、不得放宽测试**。测试数量只能增加或持平。
8. **UI 只用 Kumo**：前端不得引入新的 UI 库或新的原生控件；已有 UI 例外见 `docs/standards/重构验证与例外清单.md`，拆分时不得扩大例外范围。
9. **时区规则**：不得在业务代码引入 `time.Local` / `time.UTC` 做日期归属；沿用现有 `internal/timeutil` 用法（拆分不涉及逻辑，主要是别在搬移时改动）。
10. **单所有者文件**：`src/js/pages/ServerPage.jsx`、`src/js/pages/DnsPage.jsx`、`src/js/pages/OpenAIPage.jsx`、`src/js/components/MainLayout.jsx`、`src/js/store.js`、`backend-go/internal/server/server.go`、`backend-go/internal/manifest/manifest.go`、`backend-go/internal/serveragent/service.go` 在并行拆分时**同一时刻只能有一个子代理处理**，必须串行。

## 2. 拆分规则（核心）

### 2.1 拆分维度（分层使用，不是单一维度）

**前端 React 页面**
| 内容类型 | 归类维度 | 目标文件命名 |
|---|---|---|
| 纯常量、配置映射、枚举 | 关注点 | `constants.js` |
| 纯函数（格式化、计算、无副作用工具） | 关注点 | `utils.js` |
| 自定义 Hook（封装一个独立状态域） | 业务域 | `useXxx.js` |
| 子组件 / 弹窗 / 面板 / 表格 | 功能单元（一个可独立命名的 UI 单元一个文件） | `XxxPanel.jsx` / `XxxDialog.jsx` / `XxxTable.jsx` |
| 页面容器 | 只留编排 | `XxxPage.jsx`（组合 hooks + 渲染子组件） |

**后端 Go 服务**（受同包约束，按功能簇拆文件，不拆包结构）
| 内容类型 | 目标文件命名 |
|---|---|
| HTTP 路由分发（ServeHTTP / 注册） | `service.go`（保留） |
| 某一业务域的方法簇 | `xxx_<domain>.go`（如 `subscription_profile.go`） |
| 类型定义集中 | `types.go` |
| schema / 迁移 | `schema.go` |
| 纯工具函数 | `helpers.go` |

**关键约束**：
- 后端 `Service` 结构体字段**不拆**（拆了要改所有方法）；只把方法按域搬到新文件，`package` 保持不变。
- 一个源文件可以拆成多个目标文件；也可以按需在现有模块目录下新建子目录（模仿 `pages/openai/`）。

### 2.2 命名契约（全仓库统一，禁止同义异名）
- **禁止**混用 `utils.js` / `helpers.js` / `common.js`：前端统一 `utils.js`，后端统一 `helpers.go`。
- **禁止**混用 `constants.js` / `config.js` / `enums.js`：统一 `constants.js`。
- Hook 一律 `use` 前缀 + PascalCase（`useEndpoints.js`）。
- 组件文件一律 PascalCase，文件名 = 主导出组件名。
- 后端文件一律 snake_case，`camel_case` 仅用于 Go 标识符。
- 每个新文件**必须**只有一个明确的"主职责"，文件顶部不得有"杂项"含义的注释。

### 2.3 拆分粒度
- **按职责拆分，不设行数硬指标**。原则是"一个文件一件事"。
- 但设一条软上限：**拆分后，任何"页面容器"或"服务主文件"若仍 >800 行，必须说明为什么不能再拆**（在规划文档里写一句理由）。容器只剩编排却仍超 800 行，通常意味着状态归属没理清，需继续抽 hook。
- 不追求极致的"每文件 100 行"；自然的域边界优先于行数均匀。

### 2.4 依赖方向（防循环依赖）
- 允许的方向：容器 → 子组件 / hooks / utils / constants
- 禁止：`utils.js` 反向 import 组件；`constants.js` import 任何运行时模块；子组件之间互相 import（如必须，抽到共享的父级或 utils）。
- 拆分后必须确认无循环依赖（构建通过 + `lint` 通过即可覆盖大部分情况）。

### 2.5 导出方式
- 沿用源文件既有的导出风格（默认导出 vs 具名导出）。**不强制**改成某种风格，但同一模块内保持一致。
- 重新导出要显式：若某符号原来从 `XxxPage.jsx` 导入，拆分后如需保持旧路径可用，可在 `XxxPage.jsx` 内 `export { X } from './utils'`（仅在确有必要时，避免产生大量转发文件）。

## 3. 执行流程（三阶段，强制顺序）

### 阶段 A：侦察、基线与规划（单代理，串行，禁止并行）
1. 读取第 1.2 节列出的所有文档，提炼约束。
2. **确认基线已就绪**：`docs/refactor-baseline/` 已存在（由 `tools/refactor-snapshot.mjs` 在 `dev` 上采集）。若缺失或 `dev` 期间发生了与本重构无关的行为变更，按第 5.5.2 节重新采集。
3. **确认已在重构分支** `refactor/large-files`（第 1.0 节）。
4. 对**每一个**待拆分文件，用只读方式分析其内部结构：导出的组件/函数、内部子组件、hooks、常量、纯函数、类型、已有 section 分区、共享闭包状态、拆分障碍。
5. **规划文档已存在**：`docs/refactor/超大文件重构规划.md` 已产出，含完整的逐文件拆分映射与批次计划。执行者应**先完整阅读该规划**，不得重新设计拆分方案。若实际代码与规划不符，以规划为准并在执行中记录偏差。
6. 规划确认无误后，**停下来等待人工确认**再进入阶段 B。**不要跳过这一步。**

### 阶段 B：并行执行（子代理，按批次，全程在 refactor/large-files）
- 确认当前分支为 `refactor/large-files`，**绝不切回 `dev`/`main` 做改动**。
- 按规划文档的批次执行。**同一批次内若包含 1.1.10 列出的单所有者文件，该文件必须串行处理，不得与其他子代理并行。**
- 每个子代理认领 1–3 个源文件（并行上限建议 ≤4 个子代理，避免写冲突）。
- 每个子代理执行前必须先读规划文档中对应条目的目标拆分表，**严格照表执行**，不得自行发挥。
- 每个子代理完成后必须自检：
  - 新文件已创建，内容与源文件搬移部分逐字一致（除 import/export 调整）。
  - 原文件已删除被搬移的内容，并正确 import 新文件。
  - 无循环依赖。
- **每完成一个批次**（而非全部完成后）：
  1. 运行 `npm run lint`（前端改动）与 `cd backend-go && go build ./... && go vet ./...`（后端改动）。
  2. 运行 `npm test`（前端）与 `cd backend-go && go test ./...`（后端）。
  3. **对该批次影响范围做基线快照复采与比对**（第 5.5.3 节），确认零非预期差异。
  4. 全部通过后**立即提交**（见第 4 节提交规范），提交信息注明批次与涉及文件，并在提交信息里写明该批次的基线对比结论。
  5. 任一检查失败或存在非预期差异：回退该批次（`git checkout -- <files>` 或 `git reset --hard` 到上一提交），修复后重试，**不得带着失败进入下一批**。

### 阶段 C：全局验证（单代理，串行）
全部批次完成后：
1. 运行完整门禁（第 5 节）。
2. 做**全量基线快照复采与比对**（第 5.5.3 节），生成对比表。
3. 执行关键流程显式回归（第 5.6 节）。
4. "人类视角"抽查：随机挑 3 个拆分后的模块，确认文件职责单一、命名一致、无残留的死代码/空转发文件。
5. 产出重构结果报告（第 6 节第 8 条），然后停下来等待人工确认合并。

## 5.5 行为一致性验证：基线快照对比（核心验收）

门禁只证明"代码能构建、测试能通过"，**不证明"行为与优化前一致"**。因此必须做基线快照对比。

### 5.5.1 原则
- **在 `dev`（重构前）打基线**，在 `refactor/large-files`（重构后）复采，逐项比对。
- 对比对象是**可观测的外部行为**：HTTP 响应、构建产物、路由清单、静态资源。
- **允许的差异只有一种**：与拆分无关的、由时间戳/随机 requestId/请求顺序导致的字段。这些必须在比对脚本里显式归一化，并在报告里列明归一化规则。**其他任何差异都视为回归，必须修复或回退。**

### 5.5.2 基线采集（在 `dev` 分支上，重构开始前执行一次）

**本仓库已提供固定工具，直接使用，不要自造脚本：**
- `tools/refactor-snapshot.mjs` —— 采集快照（路由清单 + 只读接口响应 + 静态资源 + dist 入口指纹）
- `tools/refactor-snapshot-diff.mjs` —— 对比两份快照，输出 PASS/FAIL
- npm 快捷方式：`npm run refactor:snapshot` / `npm run refactor:snapshot-diff`

```bash
# 1) 构建前端（保证 dist 是 dev 的产物）
npm run build

# 2) 编译并启动后端（用独立数据目录，勿碰 data/）
cd backend-go && go build -o tmp/api-monitor-base.exe ./cmd/api-monitor
#   以 APP_ENV=development、DATA_DIR=<临时目录> 启动到 127.0.0.1:3000

# 3) 采集基线
cd .. && node tools/refactor-snapshot.mjs --out docs/refactor-baseline
```

- 基线覆盖：路由清单、15 个只读接口（含 401 边界与 404）、6 个关键静态资源、dist 入口指纹。
- 归一化规则已内置于 `tools/refactor-snapshot.mjs`，无需手工处理。
- 基线**提交到 `refactor/large-files` 分支**，作为"优化前"的不可变证据。
- **若本地已有基线且未发生无关改动，不必重采。** 当前基线已在 `docs/refactor-baseline/`。

### 5.5.3 复采与比对（在 `refactor/large-files` 上，每批完成及最终交付前）

```bash
# 重新构建 + 重启后端后：
node tools/refactor-snapshot.mjs --out docs/refactor-after
node tools/refactor-snapshot-diff.mjs --before docs/refactor-baseline --after docs/refactor-after
```

- 工具会逐项比对路由清单、接口 status/contentType/归一化 body、静态资源、dist 入口存在性。
- 退出码 0 = PASS（无非预期差异）；退出码 1 = FAIL（必须修复或回退）。
- **前端 bundle 的字节级 hash 允许不同**（拆分必然改变打包），工具只校验入口与关键资源存在性。
- **后端二进制 hash 允许不同**，但要求 `go build` + `go vet` + `go test` + smoke 全通过。
- `docs/refactor-after/` 是临时产物，验证通过后删除，**不进仓库**。

### 5.5.4 记录
在重构结果报告中，附一张对比表：每一项基线值 vs 复采值 vs 是否一致 vs 归一化说明。

## 6. 完成标准（Definition of Done）

1. 规划文档 `docs/refactor/超大文件重构规划.md` 已产出并被执行完毕，实际产物与规划一致。
2. 所有目标文件均已拆分；前端页面容器与后端服务主文件不再存在"看起来还能继续拆"的巨型单文件（确需保留超限者，已在规划文档写明理由）。

5. **基线快照对比零非预期差异（第 5.5 节），关键流程显式回归全部通过（第 5.6 节）。**
6. 测试数量不减少；所有既有测试通过。
7. 全程在 `refactor/large-files` 分支，`dev`/`main` 未被触碰；逐批提交完成，工作区干净。
8. 产出一份**重构结果报告**：拆了哪些文件、每个源文件拆成哪些目标文件、基线对比表、验证命令与结果、遗留问题（若有）。
